Timeweave

From stutter to smooth

How Timeweave's calendar learned to scroll at 90 Hz · October 2026

In short: the calendar stuttered when flicking through it. Guessing fixed a little. Measuring found two real causes: one button that rebuilt the whole screen, and day tiles so heavy that Dart's memory clean-up paused the scroll for up to 78 ms. Both are fixed; the long pauses are gone.

The setup

Timeweave is a Flutter app for Android. Its main screen is an endless vertical stream of small day tiles, four per row, each showing the weekday, the date, four dots for how busy the day is and sometimes a "!" badge. About 40 tiles are on screen at once.

The test phone was a Pixel 7. Its screen refreshes 90 times a second, so every frame has to be ready within 11.1 ms (a 60 Hz screen allows 16.7 ms). A frame that misses that window is shown one refresh late, and a few in a row are a visible hitch.

Round 1: fixing the usual suspects

Before measuring anything, a read through the code turned up four likely costs, and all four were fixed:

  • Date formatters built for every tile. Each tile created two new DateFormat objects every time it was built, and each one parses its pattern again. They are now created once and reused.
  • A rounded clip on every tile. Clipping 40 tiles is extra drawing work every frame; the tiles now draw a rounded background instead.
  • Days loaded again when scrolling back. Tasks are loaded in 4-week blocks, and a block was dropped the moment its tiles left the screen. Blocks now stay loaded for a minute.
  • Days loaded only once visible. The list now prepares about one screen ahead, so a tile's tasks are usually there before it appears.

Result: "better, but you can still see it". Sensible fixes, but none of them was the problem.

Lesson: reading code finds plausible costs, not necessarily the real ones. Measure before fixing.

Round 2: measuring frames, finding a 29 ms frame

The next step was an automated scroll test running on the phone itself in profile mode (almost release speed, but with timing data), using Flutter's integration_test package and flutter drive. It fills its own throwaway database with three years of tasks, scrolls fast and slow, and records every frame.

Getting reliable numbers took a few tries, each worth knowing:

  • The timeline recorder couldn't connect to the app until the run used --no-dds.
  • The first runs captured only about 20 frames. Profile builds keep the trace in a small ring buffer, and recording everything (compiler, VM internals) overwrote the scroll within a second or two. Recording only the Dart, Embedder and GC streams fixed it. An "endless" buffer was not the answer: it made pulling the trace off the phone hang.
  • The test framework moves time in jumps by default. LiveTestWidgetsFlutterBindingFramePolicy.fullyLive makes it draw frames at the phone's own pace.
  • Simulated finger flings barely moved the list in that mode, so the test scrolls with ScrollPosition.animateTo over fixed distances instead.
  • The test turns on accessibility (semantics) by itself, which costs about 5 ms per frame. Phones without TalkBack or similar don't pay that, so it has to be subtracted when judging frames.

With that, one frame stood out at 29 ms. Turning on per-widget build events (debugProfileBuildsEnabledUserWidgets) showed the whole screen being rebuilt in it: the app bar, the scroll view and every visible tile.

The trigger was the floating "Today" button. It appears once today's card scrolls out of view, and it was part of the screen's state, so showing it ran setState on the entire screen, right in the middle of a scroll. The same happened when it disappeared again.

// Before: showing the button rebuilt everything.
if (hidden != _showTodayButton) setState(() => _showTodayButton = hidden);

// After: only the button listens.
final _showTodayButton = ValueNotifier(false);
...
floatingActionButton: ValueListenableBuilder(
  valueListenable: _showTodayButton,
  builder: (context, show, _) => show ? FloatingActionButton.extended(...)
                                       : const SizedBox.shrink(),
),

Round 3: real fingers, real app

The scripted test was now perfect, yet a fast flick by hand still looked a bit jerky. Two things were different from the test: real touch input, and the real app instead of a test harness.

Real swipes can be sent over USB with adb shell input swipe. Inside the test this needed binding.shouldPropagateDevicePointerEvents = true, otherwise the framework ignores real touches. Even better, Android's own display system records when each frame of the real release app reached the screen, with no test code involved:

adb shell dumpsys SurfaceFlinger --latency-clear
adb shell input swipe 540 1900 540 700 90
adb shell dumpsys SurfaceFlinger --latency '<the app's SurfaceView layer>'

The gaps between those present times told the real story: mostly 11.1 ms, but regularly 22 ms (one refresh skipped), and once or twice per flick 44–78 ms, which is four to seven frames missing. That's the visible stutter.

A quick round of experiments narrowed it down, building the app with parts of the tile switched off:

Two more things were ruled out along the way: flicking only in the middle of the list (never touching the top) still showed the pauses, so Android's overscroll "stretch" wasn't the cause; and the numbers vary quite a bit from run to run, so it takes several flicks per version to compare fairly.

Lesson: a test harness is not the app. Measure the real build with real input too.

Round 4: catching the memory clean-up in the act

To see what happened inside those pauses, the real app was traced with Android's built-in Perfetto system tracer. A profile build started with an extra flag sends Flutter's own events (build, layout, garbage collection) into the system trace:

adb shell am start -W -n <app>/.MainActivity --ez trace-systrace true
adb shell "cat config.txt | perfetto --txt -c - -o /data/misc/perfetto-traces/flick.pftrace"

Read with Perfetto's trace processor, the picture was clear. Every long frame contained a Scavenge, Dart's quick clean-up of recently created objects, taking 28–56 ms. During it, the main thread mostly slept, waiting for a helper thread that was busy copying objects on one of the phone's fast cores the whole time. A scavenge normally takes a millisecond or two.

Why so slow? A scavenge copies every recently created object that is still in use. During a fast flick, those are all the new day tiles, and each tile was built from about 60 widgets, each with its element and often a render object. Material's ripple machinery (Material + InkWell) alone contributed about 25 of them, and the four dots (four boxes in a row, with padding) about 15. That's also why the plain coloured box had no pauses at all.

The fix was to build each tile from far fewer pieces while keeping its look:

  • The four dots are one CustomPaint instead of four decorated boxes. They look identical, and the Today card and day view benefit too.
  • A DecoratedBox with a GestureDetector instead of Material + InkWell. The only visible difference is that tapping a tile shows no ripple; it still opens the day straight away, and screen readers still see a button.
  • The badge layer (Stack) is only added on days that actually have a "!" or "?".

Lesson: in a list that builds many items quickly, the number of widgets per item matters. Not because building them is slow, but because they all have to survive the next garbage collection.

What's left

An occasional single skipped frame at 90 Hz, which is very hard to notice. With an accessibility service such as TalkBack switched on, the calendar does about 5 ms more work per frame and a few frames still go slightly over budget; that's on the list for later, because the app is meant to be accessible.

Takeaways

  1. Know your frame budget: 11.1 ms at 90 Hz, not 16.7 ms.
  2. Measure before fixing. The two real causes were not on the first list of suspects.
  3. Separate building (your code) from drawing (the GPU). Here, drawing was always fine.
  4. Look between frames too. The worst pauses came from garbage collection, which per-frame build times didn't show.
  5. Check the real app with real input. dumpsys SurfaceFlinger --latency needs no test code at all.
  6. Keep list items light. Fewer widgets per item means less for the garbage collector to copy.
  7. Never rebuild a whole screen for a small change during a scroll.
